Protocols

What nestlocal, the service unfr0zen installs on the thermostat, speaks on MQTT, Zigbee and Matter: enough to write an integration for any home automation system. To set the integrations up with Home Assistant, see Integrations.

All three protocols read the same state and run the same commands. A command changes the unit's settings; the state then shows what the unit did, not what was asked. A setpoint the unit adjusts or refuses comes back as the unit has it.

Conventions

  • Temperatures are °C on every protocol, whatever the unit displays. MQTT carries degrees; Zigbee and Matter carry hundredths of a degree (2150 is 21.5 °C).
  • Temperatures read as the display shows them: to 0.5 °C, or, when the unit displays °F, to the whole °F converted back to °C. The raw/ MQTT topics keep the unit's exact values.
  • Setpoints written are rounded to 0.5 °C. The unit keeps a range's low and high at least 1.5 °C apart.
  • The equipment decides what is offered. Cooling, the fan, an air filter, a humidifier and so on appear only when the unit's wiring has them (can_heat, can_cool, has_fan, has_air_filter, has_humidifier, has_dehumidifier, has_hot_water_control).
  • Nothing is offered before the unit has reported its settings to nestlocal, a few seconds after it starts.
  • The serial is the unit's serial number, which is also its hostname.

MQTT

nestlocal is an MQTT 3.1.1 client of your broker: tcp:// or mqtt:// in the clear, ssl://, tls:// or mqtts:// over TLS. WebSockets are not supported.

Watch everything, and set a temperature:

mosquitto_sub -h broker.lan -t 'nestlocal/#' -v
mosquitto_pub -h broker.lan -t 'nestlocal/<serial>/set/target' -m 21.5

Home Assistant discovery

nestlocal publishes retained discovery configs to homeassistant/<component>/nestlocal_<serial in lowercase>/<key>/config, again when the equipment changes and whenever online arrives on homeassistant/status. An entity the equipment no longer offers gets an empty retained payload. Every config reads state and names its availability topic, so a system that isn't Home Assistant can ignore discovery and use the topics above.

Components: one climate (key thermostat), and sensor, binary_sensor, switch, number, select and button entities whose key is the state field they read or the command they send.

MQTT commands

Publish to nestlocal/<serial>/set/<command>. The payload is plain text, surrounding whitespace ignored; on/off takes ON, OFF, true, false, 1 or 0, in any case. A payload out of range or unknown is logged on the unit and ignored: there is no error topic. Watch state for the result. Don't retain commands, set/weather aside: nestlocal gets every retained one again each time it connects.

Weather & clock

The unit's weather screen and its clock came from Google. Over MQTT, anything can supply them; the Home Assistant blueprints on the Integrations page are one implementation.

Weather. Publish set/outdoor_temperature and set/outdoor_humidity; without both the unit shows no weather. Optionally publish set/weather, retained so a restarted nestlocal gets it back, as JSON in Home Assistant's own names:

{
  "condition": "partlycloudy",
  "next_rising": "2026-10-31T07:12:00+00:00",
  "next_setting": "2026-10-31T17:40:00+00:00",
  "hourly": [{"datetime": "2026-10-30T15:00:00+00:00", "temperature": 12.5, "humidity": 70}],
  "daily":  [{"datetime": "2026-10-31T00:00:00+00:00", "temperature": 14, "templow": 6, "humidity": 65}]
}
  • Every field is optional. Times are ISO 8601 with an offset; temperatures °C.
  • condition is a Home Assistant weather condition: sunny, clear-night, partlycloudy, cloudy, fog, rainy, pouring, lightning, lightning-rainy, snowy, snowy-rainy, hail, windy-variant. Others show the unit's default image.
  • next_rising and next_setting choose the day or night image.
  • hourly: up to 48 hours. daily: up to 6 days. A twice-daily list (day and night halves, each with is_daytime) is folded into days, the night's temperature as the low.

Clock. nestlocal sets the unit's clock from NTP. On a network with no way out to an NTP server, it publishes an empty message on time/request every minute until answered, then every 6 hours. Answer on set/time with the current time in seconds since 1970 (decimals allowed). An answer more than 5 seconds after the request is ignored.

mosquitto_sub -h broker.lan -t 'nestlocal/+/time/request' -v | while read -r topic _; do
  mosquitto_pub -h broker.lan -t "${topic%/time/request}/set/time" -m "$(date +%s)"
done

Zigbee

The thermostat is a Zigbee 3.0 router on the Home Automation profile (0x0104), in standard ZCL clusters only: no manufacturer-specific clusters, attributes or commands. Zigbee2MQTT has a ready-made converter, which is also a working reference for a converter or quirk elsewhere.

Reports

The thermostat reports every change, and everything every 10 minutes (the first 10 s after joining), to the coordinator (0x0000), endpoint 1. It does so whatever bindings and reporting configuration exist: Configure Reporting is accepted and changes nothing. Bind and configure reporting anyway if your stack expects it; the converter does.

Reported attributes: Thermostat 0x0000–0x0002, 0x0011–0x0014, 0x001B, 0x001C, 0x0025, 0x0029; Power Configuration 0x0020; 0x0000 of Fan Control, Thermostat UI Configuration, Relative Humidity, Temperature Measurement and On/Off; PresentValue (0x0055) of Analog Output, Analog Input and Binary Input.

Commands

Read Attributes, Write Attributes (with and without response), Configure Reporting and Discover Attributes are answered. A write is a command (see MQTT commands, with the same ranges): out of range gives INVALID_VALUE, read-only READ_ONLY. A read of an attribute with no value yet gives ZCL's "none" for its type (0x8000 for temperatures, 0xFFFF for humidity, 0xFF for battery voltage).

Switches are numbered from 10 in this order, skipping those the equipment lacks: Auto-Schedule, Home/Away Assist, Sunblock, Early-On, Eco heat limit (can heat), Eco cool limit (can cool), Humidity control (with a humidifier or dehumidifier). The numbers therefore differ between units: identify each by its Fixed Label, ha_entitylabel, whose value is the name above.

Thermostat cluster

  • Features: Heating, Cooling, AutoMode, Occupancy, Presets. What the unit can do is in ControlSequenceOfOperation (read-only): heating only, cooling only, or cooling and heating.
  • SystemMode: Off, Heat, Cool, Auto (heat_cool). A mode the equipment can't do is refused with a constraint error.
  • Occupied setpoints: the range in Auto; otherwise either one sets the single target. Limits 9–32 °C, dead band 1.5 °C.
  • Unoccupied setpoints are the eco temperatures: heating 9–21 °C, cooling 24–32 °C.
  • Occupancy, OutdoorTemperature (from MQTT), ThermostatRunningState (heat, cool, fan).
  • Presets: one, handle eco (the eco temperatures). SetActivePresetRequest with eco turns eco on, with null back to the schedule. ActivePresetHandle is eco or null.
  • Commands: SetpointRaiseLower and SetActivePresetRequest. No weekly schedule.

Not on Matter: the indicators (Leaf, Early-On and Sunblock active, safety shutoff, filter, hot water, humidifier and dehumidifier running), the target humidity, time to temperature, filter runtime and clearing the schedule. Use MQTT or Zigbee for those.
